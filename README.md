# Revenue Reconciliation: CRM vs ERP vs Data Warehouse

[![checks](https://github.com/mastropasquamatteo/revenue-reconciliation/actions/workflows/checks.yml/badge.svg)](https://github.com/mastropasquamatteo/revenue-reconciliation/actions/workflows/checks.yml)

Sales says one number, finance says another, the dashboard shows a third. This project reconciles the three at record level, classifies every difference, and puts a euro amount on each type of problem.

All data is synthetic, generated by a script in this repository. No real company, customer or figure is involved.

## The problem

A fictional B2B equipment vendor tracks the same sales in three systems:

| System | What it holds | Table |
|---|---|---|
| CRM | opportunities won by sales | `crm_opportunities` |
| ERP | orders actually invoiced | `erp_orders` |
| Data warehouse | bookings shown in reporting | `dwh_bookings` |

Deals are in EUR, USD and GBP. Monthly FX rates are in `fx_rates`.

The totals for 2025 do not agree:

| | Records | Amount (EUR) |
|---|---|---|
| CRM, Closed Won | 423 | 14,294,694 |
| ERP orders | 434 | 13,898,797 |
| Data warehouse | 427 | 13,782,671 |

## Key finding

**The totals hide most of the problem.** ERP and the data warehouse differ by only EUR 116k, less than 1%. At record level the picture is different:

- 21 orders never reached the warehouse: **EUR 540,821 missing**
- 14 orders were loaded twice: **EUR 424,695 counted twice**

The two errors cancel each other out in the total. About EUR 965k of wrong records sit behind a gap of EUR 116k. Checking totals only, nobody would notice.

## Approach

Everything runs in SQL on SQLite. Python only loads the files and exports the results.

1. **Staging** (`sql/01_staging.sql`). Every amount is converted to EUR with the rate of its own month. The CRM reference typed in ERP is cleaned: spaces trimmed, upper case, underscore to hyphen.
2. **Matching CRM to ERP** (`sql/02_match_crm_erp.sql`). First by reference. For orders with no reference, a match is suggested on same customer, amount within 1% and dates within 30 days, and accepted only when the candidate is unique on both sides.
3. **Classification** (`sql/03_classify_crm_erp.sql`). ERP orders are summed per opportunity, so a deal invoiced in two orders counts as one deal. Each opportunity gets one status. The order of the rules is deliberate: a difference in money wins over a timing difference, which wins over differences that are only cosmetic.
4. **ERP to warehouse** (`sql/04_match_erp_dwh.sql`). Each order must appear exactly once, in the right month, with the right amount.
5. **Summary** (`sql/05_summary.sql`). Count and euro impact per status.

### Statuses

| Status | Meaning | Action |
|---|---|---|
| `MATCHED` | Same reference, amount, month, currency | none |
| `REFERENCE_NORMALISED` | Matched only after cleaning the reference | fix data entry |
| `FX_EXPLAINED` | CRM in USD/GBP, ERP invoiced in EUR, same value | none, not an error |
| `SPLIT_ORDER` | One deal invoiced in several orders, total matches | none, not an error |
| `SUGGESTED_MATCH` | No reference in ERP, match found on customer + amount + date | confirm and fill the reference |
| `PERIOD_MISMATCH` | Closed in one month, invoiced in the next | check cut-off rules |
| `AMOUNT_MISMATCH` | Amounts differ by more than 0.5% after FX | investigate |
| `MISSING_IN_ERP` | Won in CRM, never invoiced | investigate |
| `NO_CRM_OPPORTUNITY` | Invoiced, no opportunity behind it | investigate |
| `MISSING_IN_DWH` | Invoiced, not in the warehouse | fix the load |
| `DWH_DUPLICATE` | Loaded more than once | fix the load |

## Results

**CRM vs ERP** (423 won opportunities plus 12 orders without an opportunity)

| Status | Records | Impact (EUR) |
|---|---|---|
| MATCHED | 305 | 0 |
| REFERENCE_NORMALISED | 39 | 0 |
| SUGGESTED_MATCH | 19 | 0 |
| SPLIT_ORDER | 11 | 0 |
| FX_EXPLAINED | 2 | 0 |
| PERIOD_MISMATCH | 6 | 0 in total, wrong month |
| AMOUNT_MISMATCH | 29 | -94,840 |
| MISSING_IN_ERP | 12 | -340,567 |
| NO_CRM_OPPORTUNITY | 12 | +39,510 |

The EUR 395,897 gap between CRM and ERP is fully explained by the last three rows.

72% of won opportunities match cleanly. Another 17% match only thanks to reference cleaning, suggested matches, split orders or FX, so a naive join on the reference would have flagged them as errors when they are not.

**ERP vs data warehouse** (434 orders)

| Status | Records | Impact (EUR) |
|---|---|---|
| MATCHED | 399 | 0 |
| MISSING_IN_DWH | 21 | -540,821 |
| DWH_DUPLICATE | 14 | +424,695 |

Full record-level output: [`output/recon_crm_erp.csv`](output/recon_crm_erp.csv), [`output/recon_erp_dwh.csv`](output/recon_erp_dwh.csv), [`output/summary.md`](output/summary.md).

## Testing the rules

The generator writes the list of problems it injects to `data/injected_issues.csv`. After each run, `reconcile.py` checks every status against that list: how many injected problems were found, missed, or flagged where there was none.

| Injected problem | Injected | Found | Missed | False alarms |
|---|---|---|---|---|
| missing order | 12 | 12 | 0 | 0 |
| amount mismatch | 29 | 29 | 0 | 0 |
| period shift | 6 | 6 | 0 | 0 |
| messy reference | 39 | 39 | 0 | 0 |
| missing reference | 19 | 19 | 0 | 0 |
| invoiced in EUR | 2 | 2 | 0 | 0 |
| split order | 11 | 11 | 0 | 0 |
| order without opportunity | 12 | 12 | 0 | 0 |
| duplicate in warehouse | 14 | 14 | 0 | 0 |
| missing in warehouse | 21 | 21 | 0 | 0 |

Read this for what it is. A perfect score shows that the SQL does what it claims on the problems it was built for. It says nothing about problems nobody thought of. That is the real limit of any rule-based reconciliation, and the reason the output keeps every record instead of just the exceptions.

## Limits

- **Suggested matches need a person.** Same customer, similar amount and close dates is strong evidence, not proof. With more deals per customer, candidates stop being unique and the rule correctly gives up.
- **Tolerances are choices.** 0.5% on amounts and 30 days on dates fit this data. Real data needs them agreed with finance.
- **One issue per record.** The generator never puts two problems on the same deal. Real data does, and the rule order then decides which one you see first.
- **SQLite, not SQL Server.** The logic is standard SQL. Date functions (`julianday`, `substr` on dates) would change in T-SQL.

## Run it

```bash
pip install -r requirements.txt
python generate_data.py   # writes data/*.csv
python reconcile.py       # writes output/*.csv and output/summary.md
```

The generator uses a fixed seed, so the numbers above are reproducible.

## Repository structure

```
generate_data.py     synthetic data with injected problems
reconcile.py         loads data, runs the SQL, checks results
sql/                 the reconciliation logic, run in file order
data/                generated source tables and the injected-issue list
output/              reconciliation results
```
